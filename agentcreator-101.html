1.1 What is AgentCreator?

AgentCreator is SnapLogic's enterprise-grade platform for building LLM-powered agents, assistants, and applications. It enables organizations to harness the power of generative AI within the familiar SnapLogic Designer interface - no separate application, no coding required.

Think of AgentCreator as a bridge between your enterprise data and large language models. It's not an LLM itself; rather, it's a sophisticated framework that connects to multiple LLM providers (OpenAI, Azure OpenAI, Amazon Bedrock, Google Gemini) and orchestrates them to perform complex, autonomous tasks.

Key Concept: AgentCreator is NOT an LLM

A common misconception is that AgentCreator is a language model. It's actually a platform that connects to LLMs. Think of it like this: LLMs are the "brains" and AgentCreator provides the "body" - the pipelines, tools, and orchestration that allow those brains to take action in your enterprise environment.

Why AgentCreator?

Traditional approaches to building AI applications require significant development effort - custom code, API integration, conversation management, and more. AgentCreator eliminates this complexity by providing:

  • No-Code Development - Build agents using drag-and-drop Snaps, just like data pipelines
  • Multi-LLM Support - Switch between providers without rebuilding your application
  • Enterprise Security - Built-in governance, access control, and compliance features
  • Full Integration - Connect AI to any data source SnapLogic supports (500+ connectors)
  • Production Ready - Deploy, monitor, and scale agents in production environments

1.2 Agents vs Assistants

One of the most important distinctions in AgentCreator is understanding the difference between Agents and Assistants. While these terms are sometimes used interchangeably in the industry, they represent fundamentally different approaches in SnapLogic.

The Simple Distinction
  • Agents = Custom-built using SnapLogic pipelines (full control)
  • Assistants = Pre-packaged vendor solutions (easier setup, less control)

What is an Agent?

In SnapLogic, an Agent is a group of pipelines working together to accomplish complex, goal-based tasks autonomously. Agents can:

  • Make decisions based on LLM reasoning
  • Call multiple tools dynamically based on the task
  • Iterate through complex workflows until a goal is achieved
  • Maintain conversation context across interactions
  • Integrate with any SnapLogic-connected data source

What is an Assistant?

Assistants are managed conversation tools provided by LLM vendors themselves. Examples include:

  • OpenAI Assistants - Managed through OpenAI's API with built-in tools
  • Amazon Bedrock Agents - AWS's managed agent service

These are pre-built solutions that you configure and invoke through SnapLogic Snaps, but the conversation management and tool execution happens on the vendor's side.

Detailed Comparison

Aspect Agents (Custom-Built) Assistants (Vendor-Managed)
Control Full control over every aspect - prompts, tools, flow, logic Limited to vendor-provided configuration options
Implementation Build with Agent Snap + custom tool pipelines Configure in vendor console, invoke via Snaps
Flexibility Highly customizable - any pipeline can be a tool Restricted to vendor's tool framework
Debugging Full visibility via Agent Visualizer Limited to vendor's logging/monitoring
Data Residency Control where data flows Data processed on vendor's infrastructure
Learning Curve Steeper - requires understanding of agent patterns Gentler - simpler configuration
Time to Value Longer initial setup, more powerful long-term Faster deployment for simple use cases

When to Use Each

Use Agents When:
  • You need full control over the conversation flow and tool execution
  • Building complex, multi-step workflows with custom business logic
  • Requiring integration with multiple SnapLogic-connected data sources
  • Debugging and detailed monitoring are critical
  • Data residency and compliance require control over data flow
  • You want to leverage the full power of SnapLogic's ecosystem
Use Assistants When:
  • You want rapid deployment with minimal configuration
  • The use case fits well within vendor-provided capabilities
  • You prefer managed conversation threads and context
  • Built-in RAG capabilities meet your needs
  • You're prototyping and want to test quickly
For this course (101), we focus primarily on building Agents using the Agent Snap. This gives you maximum flexibility and teaches you the fundamental patterns. Once you master agents, using Assistants becomes straightforward - they're essentially a simplified subset of what agents can do.

2.1 Launching Prompt Composer

Prompt Composer is your dedicated workspace for developing, testing, and refining prompts. Unlike traditional prompt development where you write, save, run, and check results separately, Prompt Composer provides an integrated environment where you can see your data, write your prompt, and test against a real LLM - all in one view.

Key Concept: Prompt Composer Lives Inside Snaps

Prompt Composer isn't a separate application - it's accessed from within Prompt Generator Snaps. Each LLM provider has its own Prompt Generator Snap (OpenAI, Azure OpenAI, Amazon Bedrock, Google GenAI), but they all share the same Prompt Composer interface.

Left Section: Understanding Your Data

Input Schema Panel

This panel shows the structure and data types of your input data. It displays:

  • Field names and their hierarchy
  • Data types (string, number, boolean, array, object)
  • Nested relationships between fields

The Input Schema is crucial because it tells you exactly what fields are available to use in your prompt template. When you see a field like customer.name, you know you can reference it with {{customer.name}}.

Input Data Panel

This panel shows the actual values flowing through your pipeline. It's like a real-time preview of what data your prompt will work with.

Data Size Limit

Input Data supports up to 10MB of data. For larger datasets, consider using a sample or breaking data into smaller chunks for testing.

Center Section: Creating Your Prompt

Prompt Editor Panel

This is where you write your actual prompt using Mustache templating syntax. Key features include:

Feature Description
Syntax Highlighting Mustache expressions are color-coded for easy identification
Auto-completion Start typing a field name and get suggestions from your schema
Navigation Arrows Move between prompt versions (undo/redo)
Real-time Validation Errors in syntax are highlighted immediately
SnapGPT Assistant Panel

This panel provides AI-powered assistance for prompt creation. You can describe what you want in plain English, and SnapGPT will generate a Mustache-formatted prompt for you. We'll cover this in detail in Section 2.3.

Right Section: Testing Your Prompt

Rendered Template Panel

This panel shows the final prompt after Mustache variables have been replaced with actual values. It's a preview of exactly what will be sent to the LLM.

For example, if your template is:

Hello {{customer.name}}, how can I help with your {{issue.category}} issue?

The Rendered Template will show:

Hello Sarah Johnson, how can I help with your Billing issue?
LLM Response Panel

This panel shows the actual response from the LLM after you click "Update Response". It lets you test your prompt against real AI models without leaving the interface.

2.4 Mustache Syntax Basics

While SnapGPT can generate prompts for you, understanding Mustache syntax helps you read, modify, and troubleshoot templates. Mustache is a "logic-less" templating language - it uses special tags to insert data into text.

Why "Mustache"?

The syntax uses double curly braces {{ }} which look like a sideways mustache. Hence the name!

Basic Variables

The simplest Mustache syntax inserts a field value into your prompt:

Hello {{name}}, welcome to our service!

If your data contains {"name": "John"}, this renders as:

Hello John, welcome to our service!

Nested Fields (Dot Notation)

Access nested objects using dots:

Customer: {{customer.profile.firstName}} {{customer.profile.lastName}}
Email: {{customer.contact.email}}
City: {{customer.address.city}}

For this data structure:

{
  "customer": {
    "profile": {
      "firstName": "Sarah",
      "lastName": "Johnson"
    },
    "contact": {
      "email": "sarah@example.com"
    },
    "address": {
      "city": "San Francisco"
    }
  }
}

Iterating Over Arrays

Use {{#array}} to start a loop and {{/array}} to end it:

Array of Simple Values:
Your items:
{{#items}}
- {{.}}
{{/items}}

The {{.}} represents the current item in the loop.

Array of Objects:
Order Details:
{{#products}}
- {{name}}: ${{price}} (Qty: {{quantity}})
{{/products}}

Inside the loop, you can directly reference fields from each object.

Conditional Sections

Show content only if a field exists and is "truthy":

{{#isPremium}}
Thank you for being a Premium member! Here's your exclusive discount code: PREMIUM20
{{/isPremium}}

This section only appears if isPremium is true.

Inverted Sections (Show if False/Missing):
{{^hasOrders}}
You haven't placed any orders yet. Browse our catalog to get started!
{{/hasOrders}}

The {{^field}} syntax (caret instead of hash) shows content when the field is false, empty, or missing.

Mustache Syntax Quick Reference

Syntax Purpose Example
{{field}} Insert field value {{customer.name}}
{{#field}}...{{/field}} Loop or conditional (if truthy) {{#items}}{{name}}{{/items}}
{{^field}}...{{/field}} Inverted (if falsy/missing) {{^hasData}}No data{{/hasData}}
{{.}} Current item in loop {{#tags}}{{.}}{{/tags}}
{{! comment }} Comment (not rendered) {{! This is a comment }}

Complete Example: Customer Support Prompt

Here's a realistic prompt template combining multiple Mustache features:

You are a {{customer.accountType}} support agent for TechCorp.

Customer Information:
- Name: {{customer.name}}
- Email: {{customer.email}}
- Account Type: {{customer.accountType}}

{{#previousTickets}}
Previous Support History:
{{#tickets}}
- Ticket #{{id}}: {{subject}} ({{status}})
{{/tickets}}
{{/previousTickets}}

{{^previousTickets}}
This is a new customer with no previous support history.
{{/previousTickets}}

Category: {{issue.category}}

{{#issue.attachments}}

1. Acknowledges the customer by name
2. Shows empathy for their {{issue.category}} issue

Before building your first agent, let's understand the architecture. SnapLogic agents use a two-pipeline architecture that separates orchestration from business logic.

We recommend building agents by starting with the tool pipelines first. This makes debugging easier because you can test each tool independently before connecting it to your agent.

Pipeline Responsibilities

Pipeline Purpose Key Snaps
Agent Pipeline Receives user input, defines available tools, orchestrates the agent loop JSON Generator, Prompt Generator, Function Generator, Agent Snap
Tool Pipeline Executes actual business logic when a tool is called JSON Generator (test), Business Logic, Mapper

Key Insight: Function Generator Goes in Agent Pipeline

A common misconception is that the Function Generator belongs in the tool pipeline. Actually:

  • The Function Generator goes in the Agent Pipeline - it defines what tools exist
  • The Tool Pipeline contains only business logic - no LLM-specific Snaps
  • The Function Generator is a pass-through Snap that preserves upstream data while adding tool definitions

Development Order

Follow this sequence for best results:

  1. Build Tool Pipeline - Create the business logic first
  2. Test Tool Standalone - Validate with JSON Generator mock data
  3. Create Agent Pipeline - Set up prompts and function definitions
  4. Connect Tool to Agent - Link via Function Generator's tool path
  5. Test End-to-End - Validate complete agent behavior
Why Tool-First?

When something goes wrong with your agent, you want to know if it's the tool or the agent orchestration. By building and testing tools first, you can isolate issues more easily. If the tool works standalone but fails via the agent, you know the problem is in the agent configuration.

The Agent Snap has ONE input view that receives a combined document containing both messages and tool definitions. It uses field expressions to locate each:

  • Message payload - points to the prompt/message data
  • Tool payload - points to the function definitions

This design allows the Function Generator to be placed inline in the same pipeline.

Show Answer

The sl_role field (SYSTEM, USER, ASSISTANT, or TOOL) tells the Agent Snap how to parse and format the message before sending to the LLM. If present, only sl_role, name, and content fields are extracted.

Show Answer

AUTO - This is the recommended setting for most cases. The LLM analyzes the query and decides whether to use tools or respond with its knowledge.

Q5: What are the two input views in the In-Memory Lookup snap, and what goes into each?

Show Answer

Top/Left input: The lookup request from the agent (document with the field to match). Bottom/Right input: The reference data to load into memory (e.g., product catalog, resource list). The snap performs a join on the configured fields.

4.5 Debugging Tool Pipelines with Record Replay

While Agent Visualizer shows you the agent's thinking process, sometimes you need to debug at a deeper level - understanding exactly what data the Agent Snap sends to your tool pipelines.

The Challenge: What Does the Agent Actually Send?

When a tool pipeline fails or returns unexpected results, the first question is: "What data did the Agent Snap actually send?" The answer isn't always obvious because:

  • The agent extracts parameters from natural language
  • The data includes metadata fields you might not expect
  • Field names might not match what you configured

Solution: Record Replay Snap

The Record Replay snap captures and stores the exact data flowing through your pipeline, allowing you to see precisely what the Agent Snap sends to your tools.

Adding Record Replay to Your Tool Pipeline

1
Open your tool pipeline (e.g., get_product_info)
2
Search for "Record Replay" in the Snap palette and drag it onto the canvas
3
Insert it at the START of your pipeline - before any other Snaps:
flowchart LR subgraph "Tool Pipeline with Debugging" RR["Record Replay
(captures input)"] --> IML[In-Memory Lookup] CAT["Product Catalog
(JSON Generator)"] --> IML IML --> OUT[Output] end AGENT["Agent Snap
(sends parameters)"] --> RR
4
Configure Record Replay:
  • Mode: Set to "Record" during debugging
  • File location: Choose where to save captured data (SLDB recommended)
  • File name: Use a descriptive name like agent_input_capture.json
5
Run your agent and trigger the tool. Record Replay captures the input.

Understanding the Captured Data

When the agent calls your tool, Record Replay captures an array with the parameters at the root level plus metadata fields:

[{
  "product_id": "PROD-AGENT",
  "sl_tool_name": "get_product_info",
  "sl_method": "tools/call",
  "sl_tool_metadata": {
    "path": "/Project/tools/get_product_info",
    "tool_type": "pipeline"
  }
}]
Array Input with In-Memory Lookup

The agent sends an array containing your parameters. With In-Memory Lookup, you connect this directly to the top input - the snap automatically handles the array and extracts the join field (like product_id) for matching. During testing with JSON Generator, you can use either array format or a simple object - In-Memory Lookup handles both.

Common Debugging Scenarios

Symptom What Record Replay Reveals Fix
Tool returns null/undefined Field name mismatch (e.g., productId vs product_id) Update Function Generator parameter names to match
Join field mismatch In-Memory Lookup can't match records Verify Left path and Right path configuration match field names
Tool never receives data Empty array [] Check input view is open on first Snap
Wrong values extracted Agent misunderstood parameter requirements Improve Function Generator descriptions

Development vs Production

  • Development: Keep Record Replay in "Record" mode to capture inputs for debugging
  • Testing: Switch to "Replay" mode to test with captured real data
  • Production: Remove or disable Record Replay to avoid performance overhead

Exercise 5.1: Learn to Read Agent Visualizer

Goal: Learn to use Agent Visualizer by testing your snaplogic_success_agent pipeline with different scenarios - including intentionally broken configurations.

Prerequisites

You should have your snaplogic_success_agent pipeline with two tools:

  • get_product_info (from Section 3.2)
  • get_success_resources (from Section 3.7)
Part A: Establish a Working Baseline

First, let's confirm your agent works correctly so you know what "success" looks like.

1
Open Your Agent Pipeline

Open the snaplogic_success_agent pipeline in SnapLogic Designer.

2
Set the User Query

In the JSON Generator Snap (first Snap in the pipeline), set the user_query value to:

{
  "user_query": "What is PROD-IPAAS?"
}
3
Run and Open Agent Visualizer
  1. Validate and execute the pipeline
  2. Click on the Agent Snap
  3. Select "Visualize Agent Flow"
4
Verify Success

You should see:

  • REQUEST: Your user query
  • REASONING: LLM decides to call get_product_info
  • ACTION: Tool called with product_id: "PROD-IPAAS"
  • RESULT: Product information returned
  • Diagram: Tool node is green

This is what success looks like. Remember this for comparison.

Part B: Debug a Pipeline Configuration Error

Now let's intentionally break something and learn to diagnose it.

5
Break the Tool Path

Open your Basic Function Generator Snap and find the get_product_info function configuration.

Change the Tool Path from:

/YourProject/get_product_info

To an invalid path:

/YourProject/BROKEN_PATH
6
Run the Same Query

Keep the same user query ("What is PROD-IPAAS?") and execute the pipeline again.

7
Observe the Error in Agent Visualizer

You should see:

  • ACTION: Tool was called (LLM decision was correct)
  • RESULT: Error message - "Pipeline not found" or similar
  • Diagram: Tool node is red

Debugging Insight

The error is in the RESULT, not the REASONING. This tells you the LLM made the right decision (call the tool), but the tool pipeline configuration is wrong. Check the Tool Path in your Function Generator.

8
Fix and Verify

Change the Tool Path back to the correct value (/YourProject/get_product_info), run again, and confirm the tool node turns green.

Part C: Understand LLM Tool Selection

Learn why the LLM chooses (or doesn't choose) to call tools.

9
Test with an Ambiguous Query

In the JSON Generator, change user_query to:

{
  "user_query": "Hello, how are you today?"
}
10
Check the Visualizer

Expected: No ACTION entries - the LLM responds directly.

Key Question: Is this a bug or correct behavior?

How to tell: Check the REASONING section. The LLM should explain that no tools are needed for a greeting.

Debugging Insight

If tools aren't being called when you expect them to be, check REASONING first. The issue might be:

  • Vague function description - LLM doesn't know when to use the tool
  • Conflicting system prompt - Instructions confuse the LLM
  • Ambiguous user query - Not clearly requesting tool functionality
Part D: Distinguish Pipeline Errors from Business Logic Errors
11
Test with Non-Existent Data

In the JSON Generator, change user_query to:

{
  "user_query": "What's the status of order ORD-999?"
}
12
Analyze the Result

Observe in Agent Visualizer:

  • ACTION: get_product_info was called with product_id: "PROD-999"
  • RESULT: Returns null or "Product not found" (In-Memory Lookup returns null for no match)
  • Diagram: Tool node is likely green (pipeline succeeded!)

Debugging Insight

Green tool node + "not found" result means the pipeline worked correctly - it just didn't find matching data. This is different from Part B where the pipeline itself failed.

When debugging:

  • Red node = Pipeline/configuration error → Check Tool Path, parameters
  • Green node + error in result = Business logic → Check data, filters, mappings
Part E: Export for Collaboration
13
Download the Log

From Agent Visualizer, download the log as Markdown. This is useful for:

  • Sharing debugging sessions with colleagues
  • Documenting issues for support tickets
  • Comparing before/after when troubleshooting

Debugging Checklist

When your agent isn't working, check in this order:

  1. Is the tool being called? Check ACTION entries
    • No ACTION → Check REASONING, function descriptions, system prompt
  2. Is the tool node red or green?
    • Red → Pipeline configuration error (Tool Path, account, permissions)
    • Green → Pipeline ran successfully
  3. What's in the RESULT?
    • Error message → Check tool pipeline logic
    • Unexpected data → Check parameters passed, data sources
  4. Is the final response correct? Check AGENT OUTPUT
    • If tool worked but response is wrong → Check system prompt instructions

  • What a business logic "error" looks like (green node, "not found" in RESULT)

Glossary

Agent
A group of SnapLogic pipelines working together to accomplish complex, goal-based tasks autonomously using LLM reasoning.
Agent Snap
A simplified Snap that consolidates tool calling and chat completions into a single component, eliminating the need for separate driver/worker pipelines.
AgentCreator
SnapLogic's enterprise platform for building LLM-powered agents, assistants, and applications within Designer.
Agent Visualizer
A debugging tool that provides visual diagrams and detailed execution logs for understanding agent behavior.
Assistant
Managed conversation tools provided by LLM vendors (OpenAI Assistants, Bedrock Agents) that handle conversation management on the vendor's infrastructure.
Embedding
A vector representation of text that captures semantic meaning, used for similarity searches in RAG applications.
Function Generator
A Snap that defines tools/functions that LLMs can recognize and call during agent execution.
LLM (Large Language Model)
AI models trained on vast amounts of text data that can generate human-like responses. Examples: GPT-4, Claude, Gemini.
Message Appender
A Snap that maintains conversation history by adding messages to a message list for multi-turn conversations.
Multimodal
The ability to process multiple types of content (text, images, PDFs, audio) in a single agent interaction.
Mustache
A templating syntax used in Prompt Generator Snaps to dynamically insert data into prompts using {{variable}} notation.
Prompt Composer
A 6-panel development interface for creating, testing, and refining prompts with SnapGPT assistance.
SnapGPT for Prompts
AI-powered assistance within Prompt Composer that helps generate and refine prompts using natural language.
Tool Calling
The ability for LLMs to dynamically invoke external functions/pipelines based on the conversation context.
Tool Pipeline
A SnapLogic pipeline that performs a specific task (database query, API call, calculation) and can be invoked by an agent.
Vector Database
A database optimized for storing and searching vector embeddings, enabling semantic similarity searches for RAG applications.
